# 版番号と更新（Issue #4）

トップページ、カメラ画面、撮影画像の確認画面に「版：コミットの短いID」を表示します。
Googleログイン検証ページにも同じ版を表示します。ログイン・テキスト作成・作成待ち・
有効なトークンの保持中は`operationActive`で更新を保留し、期限の検証を中断しません。
Pagesの公開時に、対象コミットのIDをHTMLと`version.json`に埋め込みます。
表示は7桁、内部の比較は40桁を使います。

## 更新のタイミング

ページの起動時、アプリが前面に戻ったとき、Safariが前の文書を復元したときに、
`version.json`をHTTPキャッシュを使わず取得します。
新しい版がある場合は、以下がすべて満たされたときだけ同じページを読み直します。

- カメラを開始・撮影していない。
- 撮影画像を確認していない（未保存の画像を失わないため）。
- 送信待ちが0件と確認できる。
- アプリが前面にある。

保留中は現在の版で使い続け、次の起動・前面復帰時に再確認します。
通信失敗や件数不明の場合も現在の画面を維持します。
更新中はカメラの開始を受け付けません。

HTMLの再読み込みには毎回異なるURLを使い、CSS・JavaScript・静的import・manifest・アイコンにも
公開コミットのクエリを付けて、ブラウザの古いHTTPキャッシュを避けます。
公開の反映待ちで旧HTMLが返る場合は、同じ版への再読み込みを30秒間抑止してループを避けます。
時間をおいてアプリを開き直すと再確認します。
Service Workerや独自のオフライン用キャッシュは追加していません。

## 将来の送信待ち機能との接続

送信待ちの保存・再送は後続のIssueで実装します。現在は0件を返すだけです。
実装時は、`public/app-update.js`の`registerPendingUploadCounter`に、
IndexedDBから件数を読む関数を登録してから`initializeUpdates`を呼んでください。

```js
registerPendingUploadCounter(async () => {
  // 後続のIssueで、実際のIndexedDBの件数を返す。
  return await countPendingUploads();
});
```

失敗時に0を返さず、例外か不明な値を返してください。
カメラや未保存画像の状態は`initializeUpdates`に渡す関数で、切り替えの直前に読みます。
安全判定の正本は`public/update-policy.js`です。

## ローカルでの確認

```sh
npm ci
npm test
npm run build
python -m http.server 8000 --bind 127.0.0.1 --directory dist
```

`public/`は編集用のソースで「開発版」を表示し、自動更新を行いません。
`dist/`は公開用の出力で、ローカルではHEADのコミット、Actionsでは`GITHUB_SHA`を使います。
テストや開発用ファイルは公開せず、Pagesには`dist/`だけをアップロードします。

## iPhoneでの実機確認

1. このPRのマージ後、`Deploy to GitHub Pages`の成功を確認する。
2. ホーム画面からアプリを開き、トップ・カメラ・撮影画像の確認画面で、
   「版」が公開対象コミットの先頭7桁と一致することを確認する。
   初めて更新機能を導入する際、版が表示されない旧ページが残っている場合は、
   Safariで公開URLを一度再読み込みして新しい版を読み込む。
3. この更新機能を含む版を開いた状態で、次のPRをmainへマージし、Pages公開の完了を確認する。
4. カメラ映像を表示したまま操作を続け、画面や版番号が勝手に切り替わらないことを確認する。
5. 撮影画像の確認中にアプリを裏に回して戻っても、画像が残り、更新が保留されることを確認する。
6. 画像確認を終え、カメラを停止してからアプリを裏に回し、再び開く。
   新しいコミットの版番号へ切り替わることを確認する。
7. 通信できない状態で起動しても、読み込めた現在の画面が勝手に再読み込みされないことを確認する。
   オフライン起動そのものは保証しない。

送信待ちの実機確認は後続の実装時に行います。現在は自動テストで、件数が1以上・不明・取得失敗なら
切り替えないことを確認します。実機での結果はPRに記録してください。
