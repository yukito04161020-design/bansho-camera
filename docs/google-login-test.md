# Issue #6：ホーム画面からのGoogleログイン検証

サーバーを持たない構成で、全画面のアプリからログインでき、期限後の取り直しに
必要な操作が授業中に使える範囲かを確認する試作です。実機結果はまだ未確認です。
設計書7章のログイン維持方式は、この検証結果が出るまで未決のままとします。

## 試作の構成

- Issue #1に記録された公開可能なGoogleクライアントIDを`public/config.js`に設定しています。
  クライアントシークレット、APIキーは使いません。
- Google Identity Services（GIS）の`initTokenClient`を使い、権限は
  `https://www.googleapis.com/auth/drive.file`だけです。`include_granted_scopes: false`を指定し、
  応答の権限も確認します。別の権限や権限不足の応答ではドライブへ送信しません。
- 最初のログインはアカウント選択を求め、取り直しは`prompt: ""`を指定します。
  いずれもボタン操作で開始します。再同意やログイン操作が必要かは実機で記録してください。
- トークンの受信時刻、`expires_in`から計算した期限、残り秒数を表示します。
  時刻は日本時間です。裏から戻ったときは実時刻で期限を再判定します。
- トークンの値は画面・ログ・保存領域・URLに出さず、メモリにだけ保持します。
  ページを閉じる・移動する操作で破棄します。端末内でのトークン永続化は行いません。
- ログイン成功後に、Drive APIへ小さなテキストを1つ作成します。
  内容は検証名と作成日時だけで、画像・個人情報・トークンは含みません。
  ファイル名は`bansho-camera-login-test_日時.txt`で、マイドライブ直下に作成します。
  「テキストをもう1つ作成する」は押すたびに新しいファイルを1つ作ります。
- 期限切れや401応答では送信を止め、取り直しを案内します。
  通信失敗時は作成済みか分からないため、自動で再送しません。
- 裏にいる間にログイン応答が来た場合、テキスト作成はアプリが前面に戻るまで待ちます。
  作成中にページを閉じた場合は通信を中断しますが、Drive側の処理済みファイルは取り消せません。

GISのトークンモデルがサポートするのはダイアログ方式です。
コードモデルのリダイレクト方式はサーバーでのコード交換が必要になるため、
この試作には追加していません。ポップアップで全画面へ戻れない場合は、その結果を
記録し、中継サーバーなどの方式を設計書で検討します。

参考：[Google公式のトークンモデル](https://developers.google.com/identity/oauth2/web/guides/use-token-model)、
[GIS APIリファレンス](https://developers.google.com/identity/oauth2/web/reference/js-reference)、
[コードモデルとサーバーでの交換](https://developers.google.com/identity/oauth2/web/guides/use-code-model)、
[Driveのmultipartアップロード](https://developers.google.com/workspace/drive/api/guides/manage-uploads)。

## マージ後のiPhone確認手順

1. ActionsのPages公開が成功したら、iPhoneのSafariで
   <https://yukito04161020-design.github.io/bansho-camera/>を開く。
   「ホーム画面に追加」済みならアプリを閉じて開き直す。
   版番号が表示される場合は新しい版であることを確認する（版表示はIssue #4のPRで追加）。
2. ホーム画面のアイコンから「Googleログインを検証する」を開く。
   「起動方法：ホーム画面（全画面）」と見出し「Issue #6」を確認する。
   直接のURLは`/bansho-camera/login-test.html`だが、ホーム画面への追加はトップページから行う。
3. 「Googleでログインして検証する」を押し、Issue #1で登録したテストユーザーを選ぶ。
   同意画面の権限が、このアプリで使うファイルの範囲だけであることを確認する。
   ログインが完了して元の全画面アプリへ戻れるか、必要な操作を記録する。
4. 「トークンの状態：有効」、取得時刻・期限、テキストの「作成成功」を確認する。
   「作成したテキストをドライブで確認」またはDriveアプリで、名前と本文を確認する。
5. 画面の期限を基準に約1時間待つ。アプリを裏に回して待ってもよい。
   戻ったときに「期限切れ」、残り0秒、テキスト作成ボタンの無効化を確認する。
   「トークンの取り直しを試す」を押し、どの操作が必要だったかを記録する。
   ボタンを押す前の自動再取得は行わない。
6. 新しい取得時刻・期限を確認して「テキストをもう1つ作成する」を押す。
   再取得したトークンで作成できるか、Drive側でも確認する。
7. アプリを閉じて開き直す。「未取得」からログインを試し、再びパスワードなどを
   入れる必要があるか、アカウント選択や同意だけで済むかを記録する。
8. Google画面を途中で閉じた場合や拒否した場合、再試行できることを確認する。
   応答が戻らない場合はGoogle画面を閉じて「ログイン待ちを中断する」を押し、再試行する。
   ファイル作成結果が確認できない場合は、Driveを確認してから作成を再試行する。
9. 検証用ファイルは確認後、必要に応じてDriveから手動で削除する。

ローカルのHTTPサーバーでは画面と疑似APIの検証ができますが、実際のOAuthには
Issue #1で登録したPagesの生成元を使ってください。

## 自動確認

`npm test`で権限の制限、取得・期限・再取得・破棄、不正な応答の拒否、
Driveへのmultipartテキスト作成、期限切れ時の送信停止、401・403・通信失敗・不正応答、
中断した古い要求が新しいセッションを無効にしないことを確認します。
テストは偽のトークンとAPIを使い、実際のGoogleログインやDriveへの書き込みは行いません。
