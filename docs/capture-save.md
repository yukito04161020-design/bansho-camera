# 撮影とDrive保存（Issue #23）

ホームの「板書を撮影する」から使います。

1. 「授業と保存先を変更」を開き、Googleでログインします。
2. 授業名を一覧から選ぶか入力して「この授業を使う」を押します。
3. 上部の授業・回を確認します。回数は空欄で自動、入力すれば手動です。
4. カメラを開始して撮影し、等倍で確認します。
5. 「保存して次の撮影」で端末内に保存します。送信完了を待たずカメラへ戻ります。
6. 件数と送信状態を確認します。認証待ちならGoogleログインを取り直してください。

初回の授業の回一覧はオンラインで取得します。取得失敗を「回なし」と扱いません。
一度確認した授業・一覧はIndexedDBに残し、オフラインの提案に使います。
未送信の回も提案に含め、同じ日や翌日のオフライン撮影で回が取り違わないようにします。
回の衝突・名前の規則はIssue #14、Driveの重複フォルダはIssue #20の規則に従います。
オフライン保存は読み込み済みの撮影画面で利用します。Service Workerによるアプリ自体の
オフライン起動は現段階で保証していません。ページを読み込めなくてもIndexedDBの未送信は残り、
通信復帰後に開いて再認証すると再送できます。

## 画像の保持と再送

画像はJPEG（品質0.95、canvasの実寸）で保存します。
Blobと授業・回フォルダ・撮影日時をIndexedDBへ入れ、保存完了後だけ確認画面を閉じます。
失敗したら画像を残して再試行できます。
回と日付は撮影時に決め、送信が遅れても固定の宛先を使います。
送信待ちの基礎はIssue #15です。成功だけを削除し、失敗・認証切れでは残します。

Drive APIの事前生成IDを画像レコードへ記録してから、resumableアップロードを始めます。
途中の通信断や応答消失後も同じIDを使います。再送時は既存ファイルを照会し、
409のときも照会してID・名前・MIME型・サイズ・親が一致した場合だけ成功にします。
アップロードセッションURLはその試行のメモリ内だけで、IndexedDBには残しません。
中断後は必要に応じ新しいアップロードセッションを開始します。同じIDを使うため画像の重複を避けられます。
別端末からの同時フォルダ作成の制限はdocs/drive-folders.mdのとおりです。

## 認証と画面更新

Googleの権限はdrive.fileのみで、トークンはTokenSessionのメモリ内だけです。
ページを閉じるとトークンを破棄し、未送信は残します。
サーバー・リフレッシュトークン・有効期限の変更は追加しません。
裏へ回ったら進行中の通信を中断し、前面で再開します。
有効トークン保持、ログイン、一覧取得、端末内保存、撮影、画像確認、未送信がある間は更新を保留します。
各通信の認証情報と画像を送る先は固定のGoogle APIです。送信用URLのホスト・パスも検証します。

## 確認

`node --test`で撮影時の宛先、日本時間と手動指定、JPEG化、失敗時の画像保持、
必要な設定だけの永続化、IDの保存と上書き拒否、再起動後の再送、HTTP失敗、
不正なアップロードURL・メタデータ、古い401による新セッションの保護を確認します。
ブラウザでは疑似映像・模擬Google通信を使います。板書画像はテストへ入れません。

実際のGoogleログイン・Drive保存・iPhoneの挙動は[実機検証チャート](device-test-chart.md)のD・Q項目でまとめて確認します。
