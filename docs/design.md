# 板書撮影アプリ 設計書（改訂版）

Sep 29, 2026 · @高橋

## 1. 概要

授業の板書をiPhoneで無音撮影し、写っている板面を自動で切り取って、Googleドライブの授業ごと・回ごとのフォルダへ保存するWebアプリを作る。将来的には、保存した画像をAIに送って処理できるようにする。

利用者は自分だけで、なるべく早く授業で使い始めることを最優先にする。そのため、撮影と保存だけの最小限の版を先に完成させ、使いながら機能を足していく。

## 2. 前提と方針

Macを持っていないため、ネイティブアプリではなく、iPhoneのSafariで動くPWA（ホーム画面に追加して使うWebアプリ）として作る。

| 項目 | 内容 |
| --- | --- |
| 動作環境 | iPhoneのSafari（ホーム画面に追加して全画面で使う） |
| 利用者 | 自分のみ |
| 公開先 | GitHub Pages（カメラ利用に必要なHTTPSを満たす） |
| 保存先 | Googleドライブ |
| 端末内の一時保存 | IndexedDB（送信待ちの画像、設定） |
| サーバー | 原則持たない（ブラウザだけで完結する）。ログインの検証結果によっては小さな中継サーバーを置く（4.2） |
| 技術 | HTML、CSS、JavaScript（フレームワークは実装時に決定） |

設計上の方針は次のとおり。

1. 無音撮影は、カメラの映像から1コマを画像として切り出す方式で行う。標準カメラの撮影機能は使わない。
2. Googleログインは、Google Cloudのプロジェクトを「テスト中」のまま使い、自分のアカウントだけをテストユーザーに登録する。Googleの審査は受けない。
3. ドライブの権限は、アプリが作ったフォルダとファイルだけを扱う範囲（drive.file）に限る。
4. 保存する画像はフェーズで分ける。フェーズ2では切り取り機能がないため撮影したそのままの画像を保存し、これを5章のサンプル画像集の素材にする。フェーズ3以降は切り取り後の画像だけを保存し、元画像は保存しない。
5. APIキーなどの秘密情報はリポジトリにもアプリにも置かない。GoogleのクライアントIDは公開されても問題ない値として扱う。
6. AIへの送信は最終フェーズで扱う。AIのAPIキーをアプリに埋め込む方式は取らない。
7. iPhoneのSafariは、アプリが裏に回るとJavaScriptを止める。そのため「裏で送り続ける」前提の設計はせず、送信待ちのものは端末内に残して、アプリが前面にあるときに送る。
8. 授業での撮影は、学校や先生のルールに従う。

## 3. 開発体制

設計はCowork、実装はCodex、レビューはClaude Codeで分担し、GitHubのIssueとプルリクエスト（PR）で作業を受け渡す。

| 担当 | 役割 | 主な成果物 |
| --- | --- | --- |
| Cowork | 設計書の管理、Issueの作成、使用中の不満や不具合の整理 | 本設計書、受け入れ条件つきのIssue |
| Codex | 実装と自動テストの作成 | Issueごとのプルリクエスト |
| Claude Code | 設計との食い違いと安全面のレビュー | PRへのレビューコメント、修正案 |
| 自分 | 実機確認、マージ、授業での使用 | 実機チェックリストの結果 |

1機能の流れは次のとおり。

1. Coworkが設計書から機能を1つ切り出し、受け入れ条件と実機チェックリストを書いたIssueを作る。
2. CodexがIssue1つにつきPRを1つ作る。ロジック部分には自動テストを付ける。Codexは自分のパソコン上のCodex CLIで動かし、起動とpush、PRの作成はCoworkが行う（下の9）。
3. GitHub Actionsが自動テストを実行する。失敗したらCodexが直す。
4. PRが作られると、Claude Codeが自動でレビューする。修正が必須の指摘があれば、Claude Codeがその指摘だけを直してテストし、PRのブランチにpushしたうえで再レビューする。Codexや自分がpushすると、再びClaude Codeがレビューする。自動レビューは1つのPRにつき最大3回までとし、それでも指摘が残る場合は自分が判断する。
5. 自動テストの成功と、自動レビューの「問題なし」を確かめて、自分がマージすると、GitHub Pagesに自動で公開される。自分の指示があれば、マージはCoworkが代わりに行う。
6. iPhoneでアプリを開き、画面の版番号（4.7）が新しい版になっていることを確かめてから、実機チェックリストを確認する。問題なければIssueを閉じる。

技術的に実現できるか分からない点は、本実装の前に「検証Issue」として切り出す。検証Issueは最小限の試作と実機での結果報告を成果物とし、結果を設計書に反映してから本実装のIssueを作る。

2026-10-02の利用者の指示により、以後の実機検証は公開後にまとめて行う。
可読性やログインの実機結果が未確定でも実装・自動テスト・PR作成を先に進め、
未確認項目は合格扱いせず、[実機検証チャート](device-test-chart.md)に集約する。
結果が出た時点で必要な仕様修正を行う。ログイン時間の変更は引き続き保留する。

約束事とレビューのルールは次のとおり。

1. プロジェクトの約束事（2章の前提と方針、コードの書き方、テストの方針）はAGENTS.mdを正本とする。CLAUDE.mdはAGENTS.mdを読み込むだけにして、内容を二重に持たない。
2. 設計書はリポジトリ内に置き、どのツールからも同じ最新版を参照する。
3. Claude CodeのGitHub Actions連携は、Proの契約で発行したトークン（claude setup-tokenで発行し、リポジトリのシークレットCLAUDE_CODE_OAUTH_TOKENに登録する）で認証し、APIキーは使わない。
4. Claude Codeのレビューは、PRの作成と更新のたびに自動で動く。Proの利用上限を節約するため、自動レビューは1つのPRにつき最大3回、1回の作業回数に上限（max-turns）を付け、モデルは既定のSonnetを使う。手動で頼みたいときは、自分がPRで@claudeとメンションする。
5. 当初はレビューの指摘をPR上の@codexでCodexに直させる予定だったが、PR上から依頼したCodexの作業はPRのブランチにpushできなかったため（2026-09-30確認）、必須の指摘の修正はClaude Codeが行う。大きな修正や方針の変更が必要な場合は、自分がCodexに直接頼む。
6. 公開リポジトリのため、自動レビューはこのリポジトリ内のブランチからのPRだけ、@claudeのメンションは本人のコメントだけで動く。
7. 動くかどうかは自動テストに任せ、Claude Codeのレビューは設計との食い違いと安全面（ドライブの権限、秘密情報の扱い）に絞る。
8. 上限に達しやすい場合は、自動レビューを止めて@claudeのメンションだけで動かす形に戻す。
9. ChatGPTの利用枠を優先して使うため、実装は自分のパソコン上のCodex CLI（codex exec、ChatGPTアカウントでログイン）で行う（2026-10-04開始）。CoworkがパソコンのCowork作業環境でリポジトリを取得し、Issueの全文を渡してCodexを起動し、終わったらブランチをpushしてPRを作る。Codexのログイン情報とGitHubのトークン（このリポジトリだけに限定した書き込み用）は、パソコンの作業フォルダ内のリポジトリ外の場所に置き、リポジトリやIssueには書かない。CodexのクラウドやPR上の@codexは使わない。

## 4. 機能仕様と受け入れ条件

各機能の受け入れ条件は、Codexの実装目標とClaude Codeのレビュー基準を兼ねる。「自動」はテストで、「実機」はiPhoneで、「レビュー」はClaude Codeのレビューで確認する。

### 4.1 無音撮影

カメラの映像を画面いっぱいに表示し、撮影ボタンで映像の1コマを画像として切り出す。背面カメラを使い、取得できる範囲で最も高い解像度を要求する。

この方式で得られる解像度は、標準カメラの静止画より低くなる（多くは1920×1080前後、機種によっては4K程度）。板書が読めるかどうかは計画全体の前提になるため、フェーズ1の最初に検証Issueとして確かめる。検証では、実際に取得できた解像度を画面に表示し、教室の後方の席から黒板、ホワイトボード、スクリーンを撮って読めるかを確認する。読めない場合は、ズームの利用や撮影位置の工夫を検討し、それでも足りなければ方式そのものを見直す。

Issue #28では撮影画面の手動カメラ一覧をなくす（検証ページの一覧は残す）。
背面のトリプル・デュアルなど、倍率に応じたレンズ切り替えをiOSへ任せられる
仮想カメラを、ズーム能力がある場合に優先する。仮想カメラがない、または
ズーム非対応なら、指定倍率に最も近い倍率を実現できる単体カメラを選ぶ。
名称から判別できる超広角は0.5倍、広角は1倍を基準にし、取得できたズーム範囲を使う。
望遠の光学倍率・名称不明のカメラ・同等の複数候補は、名前だけでは視認性を決めない。
候補の映像から各1枚を切り出して並べ、利用者に見やすい画像を選んでもらう。
ズーム対応の仮想カメラが複数ある場合も撮り比べず、指定倍率を含む範囲とズーム範囲の広さで自動選択する。
撮り比べはズーム対応の仮想カメラがなく、単体を決められないときだけ行う。
「どのカメラが見やすいか撮り比べます」と案内し、「撮り比べる」を押してから始める。
撮影ボタンや確認画面の操作を撮り比べ開始の操作として扱わない。
選択結果は候補の組み合わせと指定倍率ごとに端末へ記憶し、次回に再利用する。
撮り比べ画像はメモリ内だけで扱い、保存・送信せず、選択終了・中断で解放する。
カメラの能力取得や映像の切り出しは画面から独立した選択ロジックと分ける。
選ばれたカメラ名と現在の倍率は映像上へ小さく表示し、解像度などの詳細は設定シートに置く。
実際の倍率を取得できない場合は、指定倍率と区別して案内する。
レンズ切り替えと画質向上は実機で確認するまで未確認とする。

撮影画面を開いている間は、画面が自動で消えないようにする（Wake Lock）。

撮影画面では映像を主役とし、授業・回の1行表示、倍率、撮影操作、送信待ち件数などを最小限に表示する。授業と保存先、ログイン、手動回数、カメラ情報は開閉パネルへまとめる。縦横と切り欠きに対応し、四隅調整画面でも画像と主要操作の領域を確保する。撮影が無効の場合は理由をボタンの近くへ日本語で表示する。撮影ステージ全体（重ねた表示を含む）の2本指操作とダブルタップではブラウザの画面拡大を抑止し、カメラの倍率だけを変更する。設定シート・時間割・確認画面の文字は、iOSの「テキストサイズ」やSafariのページ表示の拡大（ぁあメニュー）で大きくしても操作できるようにする。ホーム画面からの全画面起動ではSafariのぁあメニューがないため、iOSの「テキストサイズ」設定で文字を拡大する。Safari起動ではページ表示の拡大も確認する。ピンチによるページ拡大までは求めない（Issue #37・#41、Cowork承認済み）。

ズーム対応のカメラでは、映像上のピンチ操作と倍率バーで倍率を変更できるようにする。
倍率バーと倍率表示は撮影ステージに常時表示する。高解像度の制約でズーム能力が得られない場合は制約を戻し、ズームを優先して、そのカメラの取得可能な最大解像度を要求する。
設定シートの「カメラ情報」は授業と保存先のすぐ下に見出し付きの区画として置き、折りたたまない。開始前も区画を表示し、「カメラ開始後に表示します」と案内する（Issue #41、Cowork承認済み）。
設定シートの「カメラ情報」には、選択したカメラ名・ズーム範囲（なければ「非対応」）・取得解像度・自動選択または撮り比べが必要と判断した理由を表示する。
バーは指を離すまで待たず操作中に反映する。適用中も次の入力を受け付け、
最新の指定へ追従する。変更中の撮影は、指定した倍率の反映を待って受け付ける。

受け入れ条件：

- [ ] 自動：ズーム対応の仮想カメラを優先し、ない場合は指定倍率に応じた単体カメラを選ぶ。
- [ ] 自動：判断できない複数候補は各1枚の撮り比べと選択を求め、選択結果を端末へ記憶する。
- [ ] 実機：倍率を上げると望遠レンズへ切り替わり、板書が鮮明に写る。
- [ ] 実機：撮影画面に手動のカメラ一覧が出ない。
- [ ] 実機：撮影時にシャッター音が鳴らない。
- [ ] 実機：ホーム画面から起動しても、カメラの許可と映像表示が正常に動く。
- [ ] 実機：実際に取得できた解像度を画面で確認できる。
- [ ] 実機：教室の後方の席から撮った板書の文字が読める解像度である。
- [ ] 実機：撮影ボタンを押してから次の撮影ができるまで、待ち時間を感じない。
- [ ] 実機：撮影画面を開いている間、画面が自動で消えない。

Issue #39（Cowork承認済み）では、撮影の標準動作としてボタンを押して約0.15秒待ち、
約0.5秒の間に最大8コマを取り出して最も鮮明な1枚を採用する。
長辺800px程度へ縮小してグレースケール化し、ラプラシアンの分散で比較する。
元解像度は作業用と最良画像の2枚以下で扱い、採用画像は元解像度を保つ。
待機・取り出し時間・最大コマ数と比較サイズはconfig.jsの定数に置く。
撮影中は「撮影中…」を撮影不可理由として表示し、撮影ボタンを無効にする。
裏への移動・カメラ停止では撮影を中止して全コマを捨て、撮影画面で撮り直せる。
1コマも取れない場合だけ、押した瞬間に確保した予備の1コマを使う。
設定シートのカメラ情報に取得コマ数・採用コマ番号・鮮明さの最小最大を表示する。
以後の確認・四隅調整・保存と無音の方針は変えない。動きセンサーと重ね合わせは行わない。

- [ ] 自動：テスト内で生成した鮮明画像・ぼかし画像の列から最も鮮明なコマを選ぶ。
- [ ] 自動：処理中に保持する元解像度のコマは常に2枚以下。
- [ ] 自動：hiddenの中断では撮影画面に戻り、コマ取得なしでは1コマ撮影に戻る。
- [ ] 実機：ズームした手持ち撮影で従来より文字のぶれが少なく、確認画面まで1秒程度で無音。
- [ ] レビュー：Drive権限とトークンの扱いに変更がなく、画像ファイルを追加しない。

### 4.2 Googleログインとドライブ保存

Googleアカウントでログインし、画像をドライブに保存する。保存は撮影と切り離し、完了を待たずに撮影画面へ戻る。

ログインの維持について。サーバーを持たないブラウザアプリでは、Googleから受け取るアクセストークンの有効期限は約1時間で、長く使える更新用のトークン（リフレッシュトークン）は受け取れない。また、ホーム画面から起動した全画面モードでは、Googleのログイン用ポップアップがアプリに戻らない問題が報告されている。そこでフェーズ2の最初に検証Issueを作り、次の点を実機で確かめる。

1. 全画面モードでログインが完了し、アプリに戻れるか。
2. 約1時間後にトークンが切れたとき、どの程度の手間で再取得できるか（画面操作が必要か、自動で取り直せるか）。
3. アプリを閉じて開き直したときに、再ログインが必要になるか。

検証の結果、授業中に何度もログインし直す必要がある場合は、トークンを取り直すための小さな中継サーバーを置く方式に切り替える。この中継サーバーは4.6のAI連携と共用できる形で検討する。

送信と再送の仕組みは次のとおり。

1. 撮影した画像は、まず端末内（IndexedDB）の送信待ちリストに入れる。
2. アプリが前面にあり、通信できる状態のとき、送信待ちリストから順に送る。送信に成功したものだけをリストから消す。
3. 送信に失敗したものはリストに残し、時間をおいて再送する。アプリを開き直したときや通信が戻ったときにも再送する。
4. 送信中にトークンが切れた場合は、送信を止めて画像をリストに残し、トークンを取り直してから再開する。
5. 送信待ちの件数を画面に常に表示する。

フェーズ2の最初の版（Issue #23）は撮影画面にログイン・保存を統合し、
確認画面の保存でJPEGをIndexedDBへ確実に残してから次の撮影へ戻る。
Driveの事前生成した画像IDもPOST前にIndexedDBへ保存し、応答消失後の再送や
開き直しでも同じIDを使う。409だけでは成功にせず、ID・名前・種類・サイズ・親を確認する。
画像はresumable方式で送る。送信用のセッションURLとトークンは永続保存しない。
前面・オンラインだけで新しい送信を開始し、裏へ移ったら進行中の通信を中断する。
撮影時の授業・回・日時を宛先として保持し、送信が翌日になっても変更しない。

受け入れ条件：

- [ ] 実機：初回にログインでき、以後の再ログインの手間が検証Issueで決めた範囲に収まる。
- [ ] 実機：撮影した画像が指定のフォルダに保存される。
- [ ] 自動：アップロードが失敗したとき、送信待ちリストに残り、再送の対象になる。
- [ ] 自動：送信中にトークンが切れても、画像が失われない。
- [ ] 実機：アプリを閉じて開き直しても、未送信の画像が残っていて送信される。
- [ ] 実機：保存中も次の撮影ができ、送信待ちの件数と保存の成否が画面で分かる。
- [ ] レビュー：ドライブの権限がdrive.fileに限られ、トークンなどがリポジトリに含まれていない。

### 4.3 フォルダ構成と回数

ドライブ上に「板書／授業名／第NN回\_YYYY-MM-DD」の構成でフォルダを作る。日付は日本時間で決める。

回数は、その授業で撮影した日を数えて決める。ある授業で新しい日に初めて撮影すると次の回のフォルダを作り、同じ日の撮影は同じ回にまとめる。回数はドライブ上の既存フォルダから求めるため、アプリを入れ直しても引き継げる。

フォルダ操作は、まず画面から独立したモジュールとして準備する（Issue #20）。
マイドライブ直下から階層ごとに検索し、drive.fileで扱える既存フォルダを再利用する。
一覧は全ページを取得し、不足する階層だけ作成する。同じ親に同名フォルダが複数ある場合や、
一覧を最後まで確認できない場合は、保存先を誤らないようエラーで止める。
画面への統合と画像送信は本実装で扱い、ログイン時間の変更は利用者の指示で保留する。

最初の版（フェーズ2）では、授業を手動で選ぶ。授業未選択・回未確定でも撮影でき、確認画面の保存前に授業と回を確定する。未確定の間は保存を無効にして日本語で案内し、撮影画像を残す。回は上の規則で自動的に提案し、手動で直せるようにする。撮影しなかった回があると実際の講義回とずれるため、手動で直せることを必須とする。画面上部に現在の授業と回を常に表示し、タップで変更できる。

選択授業と取得済みの回一覧はIndexedDBに記憶する。未送信の宛先も提案へ含め、
確認済みの授業はオフラインでも撮影・端末内保存できる。
初回の授業の回一覧はオンラインで正常に取得してから保存を受け付ける。
一覧が未確認なら、その旨を表示し、未確認を空の一覧と扱って回を決めない。

受け入れ条件：

- [ ] 自動：授業名、回数、日付から正しいフォルダ名が作られる。
- [ ] 自動：同じ授業で同じ日に撮った画像は同じ回になり、別の日なら次の回になる。休講があっても回数がずれない。
- [ ] 自動：日付の境目が日本時間で判定される。
- [ ] 実機：提案された回を手動で直すことができ、直した回のフォルダに保存される。
- [ ] 実機：フォルダがない場合は自動で作られ、既存のフォルダがあれば再利用される。
- [ ] 実機：アプリを入れ直しても、ドライブ上の既存フォルダから回数を引き継げる。

### 4.4 確認画面と自動切り取り

撮影後に確認画面を表示する。黒板、ホワイトボード、スクリーンのいずれでも、板面の四隅を自動で検出して枠を表示し、指で四隅を調整できるようにする。保存を押すと、斜めから撮った画像を正面から見た形に補正して保存する。画像処理は素のJavaScriptで実装し、OpenCV.jsは使わない（読み込みが重く、依存を増やさないため）。必要になった場合は設計書を先に更新する。

この機能の導入以降は、切り取り後の画像だけを保存する（2章の方針4）。

Issue #25では、まず四隅の手動調整と透視補正を実装する。画像全体を初期の枠とし、
左上・右上・右下・左下を動かして補正後の画像を確認する。補正前・処理中・
四隅の変更後は保存を受け付けず、確認した補正画像だけをIndexedDBとDriveへ保存する。
元画像は確認中のメモリ内だけに置き、保存・撮り直し後に解放する。
交差した枠や小さすぎる範囲を拒否し、処理失敗時は元画像を残して再調整できる。
素のJavaScriptで透視変換・画素補間を行い、長辺4096・1200万画素を出力上限とする。
処理を行単位に分け、裏へ移った場合や中断操作では止める。
Issue #33では、長辺1000px以下の縮小画像をグレースケール化・ぼかし、複数の明暗しきい値で
連結領域を探し、その凸包から最大の凸四角形を推定する。元画像の座標へ戻した枠を
初期値にし、補正プレビューを自動で作る。結果が合っていれば保存を1回押すだけでよい。
面積15%未満・交差・極端なゆがみなど不自然な候補や検出不能時は画像全体の枠に戻す。
検出も行・画素群単位に分けて画面へ制御を戻し、裏への移動・中断・撮り直しで止める。
利用者が中断した場合は保存不可のまま元画像を残して手動調整できる。
Issue #37では、裏への移動・自動ロックで確認中の画像・四隅・授業と回を消さない。
裏ではカメラと画像処理を止め、前面へ戻ったら同じ確認画面を表示し、途中だった検出・補正をやり直す。
確認画面表示中は撮影画面のピンチ・撮影イベントを無効にし、等倍の画像は上下左右にスクロールできる。
撮影画面で裏へ移った場合は、前面でカメラを自動再開し、前回の倍率を復元する。失敗した場合だけ再開ボタンを表示する。
アプリを完全終了した場合の確認中画像の消失は許容する。IndexedDBの送信待ちは引き続き保持する。
合成画像で自動検証し、実画像サンプルでの精度と実機での速度は未確認として残す。

受け入れ条件：

- [ ] 自動：黒板・ホワイトボード・スクリーンを模した合成画像20種類以上（傾き・回転・ノイズ・明るさのむらあり）で、7章の仮の精度目標値を満たす。
- [ ] 自動：検出できない画像では画像全体を初期の枠にする。
- [ ] 自動：外部サンプルの精度測定は画像のない環境でスキップする。
- [ ] 自動：実画像のサンプル画像集（5章）ができてから、検出精度を測定して目標値を見直す。
- [ ] 実機：検出が合っていれば、保存ボタンを1回押すだけで保存できる。
- [ ] 実機：四隅を指で動かせ、補正後の仕上がりをプレビューで確認できる。
- [ ] 実機：検出に失敗しても、画像全体を初期の枠として表示し、手動で調整できる。
- [ ] 実機：自動検出によって確認画面を開くまでの時間が大きく遅くならない。
- [ ] レビュー：切り取り前の画像がドライブに保存されていない。

### 4.5 時間割と自動判定

時間割（曜日（月〜日）、時限（任意の表示名）、授業名、開始と終了の時刻（日本時間のHH:MM））を登録し、撮影時刻から授業を自動で判定する。設定シートから追加・変更・削除の画面を開く。判定した授業名を4.3の授業・回の1行表示と保存先フォルダ名に使い、回の決め方は変えない。授業名の検証はfolder-logic.jsの既存規則に合わせ、不正な文字を勝手に置換しない。

Issue #41（Cowork承認済み）では、追加・変更画面で既定の時限表から「1限」〜「7限」を選べる。
時限表はpublic/config.jsに置き、学校名・キャンパス名は記載しない。時刻は日本時間とする。

| 時限 | 開始 | 終了 |
| --- | --- | --- |
| 1限 | 08:50 | 10:20 |
| 2限 | 10:30 | 12:00 |
| 3限 | 13:00 | 14:30 |
| 4限 | 14:40 | 16:10 |
| 5限 | 16:20 | 17:50 |
| 6限 | 18:10 | 19:40 |
| 7限 | 19:50 | 21:20 |

選択すると開始・終了時刻が入り、その場で手直しできる。「その他（手入力）」では表示名と時刻を手入力する。
保存形式は既存のperiod文字列のままとし、既存データを読み込める。表示名が既定時限と一致するものはその時限として扱う。
変更画面を開いた時点では保存済み時刻を保持し、時限を選び直したときに既定時刻を入れる。
一覧は月〜日の曜日順、1〜7限の時限順とし、その他はその曜日の既定時限の後に開始時刻順で表示する。
同じ時限の複数授業は開始時刻順に並べる。

- [ ] 自動：1〜7限の選択で既定時刻が入り、その他では手入力できる。
- [ ] 自動：既存の自由入力データを読み込み、一致する表示名を既定時限として扱う。

開始10分前から終了10分後までを判定対象とし、余裕の分数はconfig.jsの定数に置く。
余裕を含めて重なる場合は、本来の授業時間に入っている授業を優先する。
それでも1件に決まらない場合と時間割外は「未判定」とし、手動で選ぶ。
余裕は日本時間の前後日・週の境目でも扱い、開始・終了と余裕の境界を含める。
手動で選び直した授業は、その日の該当時限（余裕を含む）で優先し、端末内に記憶する。
次の時限が本来の時間で判定された場合や日付が変わった場合には持ち越さない。
未判定の重なり中に手動で選んだ場合は、該当する時限のいずれかが続く間、同日だけ優先する。

時間割は、ドライブ上のアプリが作った「板書／設定／時間割.json」に保存する（2026-10-04、Cowork承認済み）。

端末内（IndexedDB）にも写しを持ち、オフラインでも判定する。
ドライブと端末の内容が違う場合は、JSON内の更新時刻（updatedAt）の新しい方を使う。
同時刻なら端末の内容を保持する。削除後も空の時間割と更新時刻を保存する。
未ログイン・オフラインでは端末内だけに保存し、次のログイン・通信復帰・前面復帰時に同期する。
同期前に端末内保存を完了させ、通信失敗・認証切れ・中断でも内容を残す。
前面・オンライン・有効なログインのときだけDriveへ通信し、裏に移ったら中断する。
「設定」フォルダは自動取得する授業一覧から除く。トークンの扱いと権限は変更しない。

### 4.6 AI連携

用途と方式は次のとおりとする（2026-10-04、利用者から一任を受けてCoworkが決定）。

用途：

1. 回ごとのノート（最初に作る）：回のフォルダに保存された板書の画像を読み取り、文字起こしと要点のまとめを1つのGoogleドキュメントにする。ファイル名は「第NN回_YYYY-MM-DD_ノート」とし、画像と同じ回のフォルダに置く。数式は読める形で書き写し、読み取れない箇所は推測で埋めず「判読不能」と書く。
2. 復習（必要になったら）：複数回分のノートをもとに、要点の一覧や確認問題を作る。利用者がClaudeに頼んだときに作り、定期的には作らない。

方式：

- アプリにはAIを組み込まず、AIのAPIキーも使わない。サーバーも置かない（2章の方針5・6を守る）。
- ノートは、ClaudeのGoogleドライブ連携と定期実行のタスクで作る。毎日夜に1回動き、「板書」フォルダの下で、画像があるのにノートがない回のフォルダを探してノートを作る。利用者のClaudeの契約の範囲で動き、従量課金は発生しない。
- アプリのGoogleログインはdrive.fileのままとし、ノート作りのために権限を広げない。Claudeのドライブ連携は、利用者がClaudeに許可した別の権限で読み書きする。
- 定期実行のタスクは、画像の削除や移動、ノート以外のファイルの作成をしない。すでにノートがある回は作り直さない（作り直したいときは、利用者がノートを削除するか、Claudeに頼む）。
- 板書の画像はAnthropicのサービスに送られて処理される。個人名などが写り込むことがある点は、利用者が了承している前提とし、気になる回はノートを作らないよう利用者が指示できる。

受け入れ条件：

- [ ] 実機：画像を保存した回のフォルダに、翌朝までにノートのドキュメントができる。
- [ ] 実機：ノートの文字起こしが板書と大きく食い違わない（判読できない箇所は「判読不能」と書かれている）。
- [ ] 実機：すでにノートがある回では、ノートが重複して作られない。
- [ ] レビュー：アプリのドライブ権限がdrive.fileのままで、AIのAPIキーがリポジトリにもアプリにも無い。

## 5. テストと確認

確認は、自動テスト、実機チェックリスト、サンプル画像集の3つで行う。自動で確かめられるものは自動テストに寄せ、人の手間はiPhoneでしか分からない点に絞る。

| 方法 | 対象 | 実行のタイミング |
| --- | --- | --- |
| 自動テスト | フォルダ名、回数の数え方、日付の境目、授業の判定、送信待ちリストと再送処理などのロジック | PRごとにGitHub Actionsで自動実行 |
| 実機チェックリスト | カメラ、無音撮影、解像度、ログイン、ドライブ保存、画面操作、更新と版表示 | マージ後、GitHub Pagesに公開されたものをiPhoneで確認（版番号を確かめてから行う） |
| サンプル画像集 | 自動切り取りの四隅検出の精度 | 切り取り処理を変更したPRごとに自動実行 |

サンプル画像集の作り方は次のとおり。

1. フェーズ2で授業中に撮って保存された、切り取り前の画像を集める。黒板、ホワイトボード、スクリーンをそれぞれ含める。
2. 画像ごとに正しい四隅の座標を記録し、画像とあわせて別の非公開リポジトリに置く。公開リポジトリには画像を置かない。
3. 検出結果と正解のずれを測り、目標値を満たす割合を精度として出す。

板書の画像には個人名などが写り込むことがあるため、テスト用画像はこの公開リポジトリに含めず、別の非公開リポジトリに置く。

Issue #33の自動テストでは、画像ファイルを追加せずテストコード内で板面・背景・
文字に見立てた線・ノイズ・明るさのむらを生成する。
外部サンプルの測定は `CORNER_SAMPLES_DIR` で非公開画像の場所を指定して
`npm run measure:corners` を実行する。画像なしはスキップし、実画像未確認を合格にしない。
測定データの形式と手順は [四隅検出の精度測定](corner-detection.md) に記す。
